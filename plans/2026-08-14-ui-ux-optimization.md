## 第二輪決議（2026-08-14）

### A. Claude補充的UI/UX建議（已同意，一併實作）

- **Swagger UI / Postman「Try it out」風格參數表**：每個service的表單改成「欄位表」（欄位名+說明在左、輸入框+預設值在右），取代目前單純的直向 label+input 堆疊。
- **Progressive disclosure（漸進式揭露）**：`templates.json` 每個 param 可標記 `advanced: true`；常用/必填欄位常駐顯示，進階欄位收在「顯示更多N個進階選項」的可展開區塊，不要一次全攤開造成輸入負擔。
- **「重設為預設值」按鈕**：表單裡加一顆按鈕，把所有欄位還原成預設值。
- **分類篩選chip**：搜尋框旁邊加上可點選的分類標籤（工作管理/安全稽核/...），跟文字搜尋並存。

### B. 大小寫處理

不限制使用者輸入格式，但代入SQL前依欄位性質轉大寫。**例外：IFS路徑相關參數不轉**——使用者實測過 `IFS_OBJECT_STATISTICS` 查詢對大小寫不敏感，尊重實測結果、不畫蛇添足。技術做法：`kbEngine.js` 的 `fillTemplate()` 新增逐參數的 `upper` 旗標控制，不做整段SQL字串的無差別轉換（保留未來個別欄位例外的彈性）。

### C. 查詢面過窄

把每個service「可查證過的欄位」都設計成表單參數（搭配A的progressive disclosure避免欄位太多造成負擔），技術上用字串代換的「OR trick」達成「留空=不篩選」效果（`(COL = '{x}' OR '{x}' = '')`），不改動 `kbEngine.js` 的核心比對/組SQL邏輯。只使用已從 `outputs/webfetch/rzajqpdf.pdf` 核對過的欄位名稱，不臆測未驗證的欄位。

**Timestamp類參數**：兩種做法都做——
1. 「相對天數」（如：查詢N天內密碼到期、上次登入超過N天），數字輸入代入 `CURRENT_TIMESTAMP - N DAYS` 之類的運算式，不需要使用者理解IBM i的timestamp格式。
2. 「進階datetime-local選擇器」（如：`OUTPUT_QUEUE_ENTRIES` 查詢某時間點之前建立的緩衝檔），用原生 `<input type="datetime-local">`，送出時轉換格式再代入 `TIMESTAMP('...')`，收在進階選項區，不干擾一般情境。

### 範圍邊界

`OBJECT_LOCK_INFO` 的 table function 語法bug（見 `outstanding-tasks.md` 第1項）這輪不修正本體語法，只加上大小寫轉換（正交於語法對錯）；`IFS_OBJECT_STATISTICS` 的參數簽名仍未驗證，這輪不擴充篩選欄位。
